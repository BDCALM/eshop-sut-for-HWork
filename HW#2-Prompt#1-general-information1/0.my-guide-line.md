# Hướng dẫn thực hiện HW#2 cho thư mục Submission

## 1. Phạm vi bài làm cá nhân

Bạn thực hiện đúng 4 phạm vi sau:

| Pool | Phạm vi | Tên dùng trong báo cáo |
| --- | --- | --- |
| Pool A | **FR-05 - Product listing and search** | Product listing/search |
| Pool B | **FR-11 - User order history** | User order history |
| Pool C | **FR-19 - Admin user management** | Admin user management |
| Pool D | **FR-20 - Mobile application**, chỉ phần **mobile product browsing and order history** | Mobile product browsing/order history |

FR-20 là feature duy nhất của Pool D nên các thành viên có thể cùng ghi
FR-20. Để tránh trùng công việc, bài của bạn chỉ kiểm thử phần duyệt sản phẩm
trên mobile và xem lịch sử đơn hàng trên mobile. Không mở rộng sang mobile
authentication, profile, cart, checkout hoặc cancellation nếu nhóm đã giao các
phần đó cho thành viên khác.

Trong suốt quá trình, phải tuân thủ
[SKILLS-Domain-Testing.md](./Submission/SKILLS-Domain-Testing.md), đặc biệt:

- chỉ thực hiện **một Step hoặc Sub-step trong mỗi lượt làm việc**;
- không tự bịa tên field, button, thông báo lỗi, DOM hoặc expected result;
- phải có Domain Testing trước, sau đó mới làm BVA;
- test case phải có một mục tiêu, có dữ liệu cụ thể, expected result kiểm chứng
  được và có cleanup;
- bug description và root-cause analysis phải do bạn tự viết;
- không tự gán `VALID`, `INVALID`, `INCOMPLETE` cho sản phẩm AI trước khi bạn
  review và cung cấp nhận xét của mình.

## 3. Chuẩn bị trước khi kiểm thử

### 3.1. Xác nhận phạm vi với nhóm

Trước khi viết test:

1. Ghi lại bốn phạm vi ở trên trong `README.md`.
2. Xác nhận với nhóm rằng FR-05, FR-11 và FR-19 không bị thành viên khác
   kiểm thử trùng.
3. Ghi rõ FR-20 được chia theo subsection và subsection của bạn là
   **mobile product browsing and order history**.
4. Thống nhất quy ước ID test case, ví dụ:
   - `TC-FR05-*` cho product listing/search;
   - `TC-FR11-*` cho web/API user order history;
   - `TC-FR19-*` cho admin user management;
   - `TC-FR20-MOB-*` cho mobile browsing/order history.

Phần này cập nhật trong `README.md`. Mọi trao đổi/prompt dùng để xác định
phạm vi ghi nguyên văn vào `chatlog.md`.

### 3.2. Thu thập specification và bằng chứng triển khai

Đọc `feature_inventory.md` và đối chiếu source code/UI thực tế trước khi tạo
expected result:

- FR-05: `frontend-web/src/pages/Home.jsx`,
  `frontend-mobile/App.js`, `GET /api/products?search=...`;
- FR-11: mobile order-history flow, `GET /api/orders/my-orders`,
  `GET /api/orders/:id`, và user order UI nếu có;
- FR-19: admin user-management UI, backend admin-user endpoints;
- FR-20 subsection: `frontend-mobile/App.js`.

Lưu lại các URL, route, API, field, button, thông báo, trạng thái loading và
empty state đã xác minh vào phần “Environment and evidence” trong
`test-case-report.md`. Nếu chưa xác minh được UI, chỉ ghi câu hỏi/điểm cần
kiểm tra; không tự điền tên giả.

## 4. Quy trình bắt buộc cho từng feature/subsection

Thực hiện quy trình dưới đây độc lập cho FR-05, FR-11, FR-19 và FR-20
subsection. Không gộp nhiều gate vào một lượt.

### Bước A - Phân tích feature và Equivalence Partitioning

Trong `reports/test-case-report.md`, tạo một mục riêng cho feature với các
phần:

1. **Requirement and scope**: chép/tóm tắt requirement đã kiểm chứng, nêu rõ
   phần nằm trong và ngoài scope.
2. **Input variables**: ví dụ search text, authenticated user, order owner,
   product/user identifier, admin identity, network/data state.
3. **Output variables/system state**: danh sách sản phẩm, empty result,
   loading/error state, orders thuộc user hiện tại, dữ liệu user admin nhìn
   thấy, password không bị lộ, mobile navigation/state.
4. **Input/Output Equivalence Classes**: tách valid và invalid classes.
   Mỗi class có representative value và nguồn chứng cứ.
5. **Minimum Domain Test Cases**: valid classes có thể multi-cover; mỗi invalid
   case chỉ thay đổi một invalid class, các biến còn lại giữ nominal valid.

Các gợi ý cần xem xét, nhưng chỉ đưa vào báo cáo sau khi xác nhận với
spec/source/UI:

- **FR-05**: danh sách có dữ liệu, search rỗng, exact/partial match, không có
  kết quả, ký tự đặc biệt, loading và request/error state.
- **FR-11**: user có nhiều/không có order, chỉ xem order của chính mình,
  order ID hợp lệ/không hợp lệ, các status hiển thị, unauthorized access.
- **FR-19**: admin xem danh sách user, password không xuất hiện, xóa user
  khác, không xóa được chính admin đang đăng nhập, user ID hợp lệ/không hợp lệ,
  empty/error state.
- **FR-20 subsection**: mobile product list có dữ liệu/empty/loading/error,
  mở product hoặc điều hướng liên quan nếu thuộc scope, order history của
  user hiện tại, không hiển thị order của user khác, mobile back/navigation.

Sau khi hoàn tất bảng A, dừng để bạn review. Ghi các thay đổi của bạn và
prompt/response liên quan vào `chatlog.md`; ghi artifact AI và nhận xét sơ bộ
để xử lý sau trong `9.(draft)AI-Audit-Report.md`.

### Bước B - Boundary Value Analysis

Trong cùng mục feature ở `test-case-report.md`:

1. Lập bảng boundary với LB, UB, precision unit `alpha`, và nominal value.
2. Với boundary có thứ tự, xem xét `LB-1`, `LB`, `LB+1`, `UB-1`, `UB`,
   `UB`, `UB+1` khi phù hợp.
3. Nếu requirement không quy định giới hạn, không tự tạo một con số giới hạn;
   ghi “chưa xác định” và tìm giới hạn từ UI/source/API.
4. Mỗi test BVA chỉ thay đổi **một biến**, các biến khác giữ nominal valid.
5. Ghi rõ boundary của string length, page/search input, ID, số lượng bản ghi
   hoặc trạng thái nếu các boundary đó thực sự tồn tại.

Đối với FR-05, chú ý giới hạn/behavior của search text và kết quả 0/1/nhiều
item. Đối với FR-11 và FR-20, chú ý 0/1/nhiều order và quyền truy cập. Đối
với FR-19, chú ý danh sách 0/1/n user, user hiện tại so với user khác và
boundary của identifier. Chỉ dùng các giá trị đã có căn cứ.

Sau Gate B, dừng và ghi việc xác minh boundary vào `chatlog.md`.

### Bước C - Thiết kế và thực thi test case

Trong `reports/test-case-report.md`, chuyển các domain/BVA case thành test case
chuẩn:

- một case có một objective;
- tiêu đề theo mẫu `Action + Function + Condition`;
- có precondition, test data, action steps, expected result, actual result,
  status và cleanup;
- procedure không quá 15 bước;
- dùng Data Matrix khi procedure giống nhau và chỉ data thay đổi;
- dùng Step-by-Step cho flow nhiều bước;
- mỗi case trace được về `FR-05`, `FR-11`, `FR-19` hoặc `FR-20`;
- không dùng “works properly”; expected/actual phải quan sát được;
- không viết “click Submit/Login/etc.” nếu label thực tế chưa được xác minh.

Thực thi trên SUT và cập nhật các cột:

`Designed | Executed | Passed | Failed | Not yet executed`.

Mỗi failed case phải có liên kết tới ảnh trong `reports/screenshots/` và,
không thay cho bug report, một bug ID tham chiếu trong `bug-report.md`.

### Bước D - Bug reporting và AI audit

#### Bug report

Trong `reports/bug-report.md`, bạn tự viết toàn bộ nội dung bug:

- bug ID và feature/test-case liên quan;
- title;
- precondition và dữ liệu;
- steps to reproduce;
- expected result;
- actual result;
- severity/priority;
- environment;
- evidence link;
- GitHub Issue link nếu nhóm đã tạo.

AI không được viết thay `Bug Description` hoặc `Root Cause Analysis`. Nếu
chưa có bug, ghi rõ số bug là `0` thay vì tạo nội dung giả.

#### AI Audit Report

Trong `9.(draft)AI-Audit-Report.md`, ghi từng artifact AI đã được bạn review
theo 5 cột bắt buộc:

1. Prompt + tool + timestamp;
2. AI output hoặc IDs/tóm tắt trung thực;
3. `VALID`, `INVALID` hoặc `INCOMPLETE` do **bạn** quyết định;
4. Reasoning dựa trên ISTQB/lecture;
5. Student fix, bổ sung hoặc thay đổi cụ thể.

Không điền verdict/reasoning/student fix trước khi bạn thực sự review output
và thực thi/đối chiếu test case. Cuối file thêm bảng tổng kết số lượng và phần
trăm `VALID`, `INVALID`, `INCOMPLETE`.

#### AI Critique

Trong `10.(draft)AI-Critique.md`, viết:

- AI đã hỗ trợ ở bước nào;
- output nào đúng, sai hoặc thiếu;
- vì sao AI bỏ sót case (prompt/context, giới hạn LLM, độ phức tạp SUT);
- bạn đã sửa/bổ sung gì;
- giới hạn của AI và cách bạn kiểm soát hallucination;
- audit conclusion dài 80-150 từ nếu yêu cầu của môn nằm trong file này.

Phần critique phải phản ánh trải nghiệm thực tế của bạn, không tự nhận kết
quả chưa được kiểm chứng.

## 5. Cách điền từng file sau khi hoàn tất

### `Submission/reports/test-case-report.md`

Nên dùng cấu trúc:

1. Environment, build/version và dữ liệu test;
2. FR-05 - Product listing and search;
3. FR-11 - User order history;
4. FR-19 - Admin user management;
5. FR-20 subsection - Mobile product browsing and order history;
6. bảng tổng hợp designed/executed/passed/failed/not executed;
7. tổng số bug và liên kết sang `bug-report.md`;
8. giới hạn/chưa thực thi và lý do.

Mỗi mục feature phải có đủ A (domain), B (BVA), C (test cases/execution), và
traceability. Không đưa bug description của bạn sang file AI audit.

### `Submission/reports/bug-report.md`

Chỉ chứa các bug bạn đã quan sát hoặc xác nhận. Dùng evidence thật. Nếu một
bug ảnh hưởng nhiều test case, ghi một bug ID duy nhất và liệt kê các case
tham chiếu.

### `Submission/README.md`

Hoàn thiện:

- bốn feature/subsection và ownership;
- self-assessment table theo rubric;
- tổng số test cases designed/executed/passed/failed/not executed;
- tổng số bug;
- link tới report, AI audit, critique, commit log, video và referenced links;
- ghi chú về việc FR-20 được chia subsection trong nhóm.

### `Submission/chatlog.md`

Mỗi prompt/response ghi theo thứ tự thời gian, tối thiểu gồm:

```text
Time:
Feature:
Step/Gate:
Tool:
Prompt:
Response summary:
Student review/correction:
```

Khi cần audit verbatim, lưu nguyên văn prompt và response; không chỉ ghi tóm
tắt. Không đưa dữ liệu cá nhân hoặc secret vào chatlog.

### `Submission/12.(draft)Git-Commit-Log.txt`

Ghi commit hash, thời gian, message và nội dung bước tương ứng. Nên có commit
riêng sau các mốc:

1. domain partitioning;
2. BVA;
3. test-case refinement;
4. execution/bug evidence;
5. final report.

Không push remote hoặc mở GitHub Issue tự động nếu chưa có xác nhận cần thiết.

### `Submission/reports/screenshots/`

Lưu screenshot có bằng chứng cho:

- normal, loading, empty và error states;
- boundary input;
- failed test/actual result;
- mobile screen và order-history ownership;
- admin password masking và self-delete restriction.

Tên file phải liên kết được với feature/test case. Không chụp hoặc lưu dữ liệu
cá nhân không cần thiết.

### `Submission/reports/video-&-referenced-links.md`

Thêm link video demo end-to-end cho từng feature/subsection hoặc theo cách
nhóm thống nhất. Video cần cho thấy việc dùng SKILLS, từ requirement/domain,
BVA, test case đến execution/evidence. Thêm các referenced links được sử dụng,
ví dụ specification, ISTQB và repository; ghi rõ mục đích của từng link.
