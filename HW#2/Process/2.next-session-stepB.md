### 6.1 Identify ordered domains

For every approved Step A class that has a genuinely ordered domain, identify:

- variable/domain;
- lower boundary (LB);
- upper boundary (UB);
- precision unit `alpha`;
- valid nominal representative;
- smallest/largest UI-allowed value, if the UI defines one;
- evidence source.

Potential domains to investigate, without assuming they have numeric limits:

- FR-05: search string length if a UI/API/source limit exists; result
  cardinality 0/1/multiple; empty versus non-empty search.
- FR-11: order count 0/1/multiple; order identifier format/range only if
  specified; supported status set boundaries only if a meaningful ordered
  domain exists.
- FR-19: user-list cardinality 0/1/multiple; user identifier only if its
  accepted format/range is specified; current-admin versus other-user is a
  categorical partition, not automatically a numeric BVA boundary.
- FR-20: mobile search length/result cardinality and order count, subject to
  the same evidence requirements.

If no real LB/UB is specified or discoverable, write **`Unresolved`** and
explain why. Do not create arbitrary limits such as 255 characters.

### 6.2 Generate boundary points

For each justified ordered boundary, generate:

- `LB - alpha`
- `LB`
- `LB + alpha`
- `UB - alpha`
- `UB`
- `UB + alpha`

Use an appropriate `alpha`:

- `1` for integer/count/ID boundaries;
- `0.01` for currency/decimal boundaries if such a boundary is actually
  specified;
- one character for string-length boundaries;
- another unit only when supported by the evidence.

For a discrete set such as order status, do not force numeric BVA. Use
equivalence/set analysis unless the requirement defines an ordered transition
boundary.

### 6.3 Apply one-variable-at-a-time control

Each BVA test must vary exactly one variable. Keep all other variables at
their valid nominal representatives. Never combine two invalid boundary
values in one test.
